# Reliability and performance audit, 2026-09-26

Reviewed against commit `9f696123d75bd411a2ac7020f0f898dbdafcf15b` and the
accepted architecture. This pass covered the host client, raw-image and FAT
backends, protocol/CLI, firmware core, USB adapter, network/WebSocket adapter,
main loop, TinyUSB extension, and test/build workflow. Existing user edits to

## Confirmed issues fixed

| Issue | Trigger and consequence | Fix and regression |
| --- | --- | --- |
| Directory lock can be removed by an old owner | Close instance A, open B, close A again: B's lock disappears, allowing another writer. | Track whether each instance still owns its lock. Regression verifies repeated close cannot unlock B. |
| Interrupted-export evidence can be replaced | Publication fails after creating the recovery marker but before changing host files; another export overwrites the marker and can complete, bypassing the documented recovery gate. | Check the marker on every export, as well as attach. Injected publication failure verifies retry fails and preserves the exact marker and original file. |
| Uncertain commands retain session ownership | A command is received but its reply is lost, or the caller cancels. The client abandons the reply but previously left the connection open; held HID input or media could remain active. | Timeout/cancellation closes the WebSocket. Fake-server regressions verify disconnection for both cases. Reconnect and storage reattachment are explicit. Already delivered actions/writes cannot be undone. |
| Request deadline excludes sending | A request waits for the send lock or socket backpressure before its timeout starts. | Apply one deadline across sending and waiting for the response. Regression holds the send lock and verifies the request still times out. |
| Unchanged flushes rewrite all ordinary files | Every directory flush stages, fsyncs, backs up, and replaces all files even when content has not changed; this also changes file identity and modification times. | After full FAT and host-baseline validation, compare image-content hashes and skip publication when unchanged. Regression preserves file identity/timestamps over repeated flushes. |

The three initial storage regressions and both uncertain-command regressions
were run against the original implementation and failed, then passed with the
fixes. Existing changed-content export, deletion, recovery, malformed FAT,
host-edit detection, and independent FAT-tool tests continue to pass.

## Performance evidence and limits

The synthetic benchmark uses one 16 MiB file on WSL's temporary filesystem,
imports it, then measures five unchanged exports. It counts fsync and replacement
calls with wrappers. A same-environment before/after sample gave:

| Measurement | Before | After |
| --- | ---: | ---: |
| Five unchanged exports | 0.4386 s | 0.1513 s |
| fsync calls | 20 | 5 |
| file replacement calls | 15 | 0 |

Reproduce with `python tools/benchmark_export.py` in the project's Python
environment. Timing depends on cache state and filesystem; this is a local host
benchmark, not a radio or USB throughput result. Every export still fsyncs the
image and validates host contents and FAT metadata. Every write still fsyncs
before acknowledgment. Changed exports retain the existing publication/recovery
procedure, with an additional image-content read/hash pass before staging; no
speed improvement is claimed for that case.

The recorded physical raw-image rates of 0.223 MiB/s write and 0.247 MiB/s read
are not explained by directory export: raw-image mode does not run that code.
The single outstanding batch, host persistence latency, wireless power saving,
and USB scheduling remain profiling candidates, not confirmed defects. Compare
network-only, host persistence, and end-to-end USB timings before changing the
pipeline or durability contract. No speculative firmware optimization was made.
